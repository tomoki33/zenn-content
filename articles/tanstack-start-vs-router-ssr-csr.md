## はじめに

実務の技術選定で「TanStack Startという選択肢もあるのでは」と言われ、TanStack StartとTanStack Routerの違いを調べることになりました。ところが、いざ調べ始めると、前提となるSSR・CSR・SSG・SPAの理解が自分の中で曖昧なことに気づきました。

そこでこの記事では、まずSSR・CSR・SSG・SPAという言葉を整理し、その上でTanStack RouterとTanStack Startの違いをまとめます。

## 1. SSR・CSR・SSG・SPAの違い

この4つを整理する上で一番大事なのは、**そもそも同じ軸の話をしていない**と気づくことです。自分が混乱していた根本原因はここにありました。

| 軸 | 何を表すか | 選択肢 |
| --- | --- | --- |
| アプリケーション構造 | ページ遷移のたびに画面全体を作り直すかどうか | SPA / MPA |
| レンダリング戦略 | HTMLを「いつ・どこで」生成するか | CSR / SSR / SSG（/ ISR） |

つまり **SPAは「アプリの作り」の話**、**SSR/CSR/SSGは「HTMLの作られ方」の話**で、そもそも比較する土俵が違います。この2軸は独立しているので、組み合わせは実は自由です。

- SPAだけどSSR（初回表示だけサーバーでHTMLを組み立て、以降の画面遷移はJSがハンドリングする）
- SPAでCSR（最初から最後までブラウザ側でHTMLを組み立てる、いわゆる従来型のSPA）
- MPAでSSR（ページ遷移のたびにサーバーへリクエストし、都度HTMLを生成する昔ながらの作り）

「SSRなのにSPAみたいに遷移する」という組み合わせが存在するのが混乱ポイントで、ここを先に押さえておくと後の整理がスッキリします。

### SPA / MPAをざっと整理

- **SPA（Single Page Application）**：最初に1回だけHTMLを読み込み、以降の画面遷移はJavaScriptがDOMを書き換えることで実現する。ブラウザのフルリロードが発生しない。
- **MPA（Multi Page Application）**：画面遷移のたびにサーバーへリクエストし、HTML全体を返してもらう、いわゆる従来型のWebサイトの作り。

TanStack Router・TanStack Startはどちらも基本的にSPA的な画面遷移（クライアントサイドルーティング）を前提にしたフレームワークです。違いはこの後の「レンダリング戦略」側にあります。

## 2. レンダリング戦略を1つずつ整理する

ここからは「HTMLをいつ・どこで作るか」という軸を整理します。

### 2-1. CSR（Client-Side Rendering）

サーバーは中身がほぼ空のHTML（`<div id="root"></div>`のようなもの）とJSファイルだけを返し、**ブラウザ側でJSを実行してHTMLを組み立てる**方式です。

- 初回表示時、JSのダウンロード・実行が終わるまで画面はほぼ空
- 画面遷移以降は基本的にサーバーへHTML全体をリクエストし直さない
- ビルド後の成果物は静的ファイル（HTML/JS/CSS）のみなので、**実行時にアプリケーションサーバーを常駐させる必要がない**

素のTanStack Router（Vite + React構成）はここに分類されます。

### 2-2. SSR（Server-Side Rendering）

**リクエストが来るたびに、サーバー側でHTMLを組み立てて返す**方式です。

- ユーザーがアクセスするたびに、サーバー上でReactコンポーネントを実行してHTML文字列を生成する
- 返ってきたHTMLはブラウザで即座に表示でき、その後JSが読み込まれて操作可能になる（ハイドレーション）
- 画面ごとに動的な処理が必要なので、**リクエストを捌き続けるアプリケーションサーバーが常駐している必要がある**

TanStack Startはデフォルトではこの動きをします。

### 2-3. SSG（Static Site Generation）

**ビルド時（デプロイ前）にあらかじめHTMLを生成しておき、実行時はその静的ファイルを配信するだけ**の方式です。

- リクエストのたびにHTMLを作り直さない。全ユーザーに同じ静的ファイルを返す
- CSRと同様、実行時にアプリケーションサーバーは不要（CDNや静的ファイルサーバーで配信できる）
- CSRとの違いは「初回表示時点で完成されたHTMLが返ってくるか」どうか。SSGは事前生成済みのHTMLがそのまま返るが、CSRは空のHTMLが返り、その後ブラウザがJSでHTMLを組み立てる

:::details ISRについて（軽く触れる程度）
Next.jsなどには**ISR（Incremental Static Regeneration）**という、SSGとSSRのハイブリッドのような戦略も存在します（一定時間ごと、またはオンデマンドで静的HTMLを裏側で再生成する）。今回の整理では深追いしませんが、「SSR・CSR・SSGだけが全てではない」というのは頭の片隅に置いておくと良さそうです。
:::

### まとめ表

| | いつHTMLを生成？ | どこで生成？ | リクエスト毎にサーバー処理が必要？ | 実行時に常駐サーバーが必要？ |
| --- | --- | --- | --- | --- |
| **CSR** | リクエスト後（ブラウザ側） | クライアント | 不要（静的ファイル配信のみ） | **不要** |
| **SSR** | リクエストの都度 | サーバー | 必要 | **必要** |
| **SSG** | ビルド時（事前） | サーバー（ビルド環境） | 不要（静的ファイル配信のみ） | **不要** |

## 3. 「サーバーが要る」の実態を整理する

この表で一番重要だと思っているのが、一番右の列「実行時に常駐サーバーが必要か」です。

- **CSR・SSG**：ビルドしてしまえば成果物は静的ファイルだけ。配信するのはCDNや静的ファイルサーバーで十分で、リクエストごとに動的処理を行うアプリケーションサーバーは不要
- **SSR**：ユーザーのリクエストが来るたびにサーバー側でコードを実行してHTMLを組み立てる必要があるので、常にリクエストを処理し続けるアプリケーションサーバーのプロセスが必要

つまり「SSRを採用する」という判断は、体感的な速度やSEOのメリットを得る代わりに、**「リクエストを処理する常駐サーバー」を運用に組み込む**という判断でもある、ということです。

たとえば「サーバーを立てる場合はアクセスログ・監査ログを残す義務がある」といった制約を持つ環境（金融システムなどはその典型です）では、この違いがそのまま技術選定の分かれ目になります。SSRを選ぶ＝常駐するアプリケーションサーバーの運用・ログ設計が必要になる、CSR/SSGを選ぶ＝静的ファイル配信だけで完結しうる、という前提を押さえておくだけで、「なぜこの構成にしたのか」を技術的な根拠を持って説明できるようになります。

## 4. TanStack Router単体（Vite + React）とは

TanStack Routerは、Vite + Reactの上に載せて使う**型安全なクライアントサイドルーティングライブラリ**です。あくまで「ルーティング」に特化していて、サーバー機能は持ちません。

- URLパラメータやクエリパラメータの型を、TypeScriptの型として自動推論してくれる（存在しないルートやパラメータ名を書くとコンパイルエラーになる）
- ネストしたルート定義、ルートごとの`loader`（データフェッチ処理をルートに紐づける仕組み）、Devtoolsなどを備える
- ただし`loader`はあくまで**ブラウザ上で実行される**。サーバー側で何かを実行する仕組みは持っていない

そして一番のポイントが、ビルドした結果です。TanStack Routerはビルドすると、最終的に静的なHTML/JS/CSSのバンドルが出力されるだけです。デプロイ先はS3+CloudFrontのような静的ファイルホスティングで完結し、Node.jsなどのランタイムサーバーを常駐させる必要がありません。

つまり、前章の分類でいう**CSR（かつSPA）**にきれいに当てはまる構成です。

## 5. TanStack Startとは何か

TanStack Startは、TanStack Router・Vite・Nitro（サーバーランタイムを抽象化するツール）の上に構築された**フルスタックのReactフレームワーク**です。TanStack Routerのルーティングの仕組みをそのまま使いつつ、以下のようなサーバー機能が追加されます。

- **SSR**：`loader`がサーバー側でも実行され、初回アクセス時点で完成済みのHTMLを返せる
- **Server Functions**：クライアントのコードから、サーバー側の関数を直接呼び出せる仕組み（Next.jsのServer Actionsに近い）
- **Server Routes**：独自のAPIエンドポイント（いわゆるAPI Routes）をアプリ内に定義できる
- **Streaming SSR**：HTMLの一部を先に返し、残りを後から流し込む

そして重要なのが、**TanStack Startのデフォルトの挙動はSSR**だということです。つまり前章の分類でいう「SSR」に該当し、ユーザーのリクエストが来るたびにサーバー側（Nitroのランタイム）でコードが実行されます。立ち位置としてはNext.jsやRemixと同じ「フルスタックReactフレームワーク」ですが、TanStack Router由来の型安全性をそのまま引き継いでいるのが特徴です。

## 6. 誤解しがちなポイント：TanStack Startは「常にSSR」ではない

ここが今回一番「知らなかった」ポイントでした。TanStack Startは名前や立ち位置から「SSR専用のフレームワーク」だと思い込みがちですが、実際には**ルート単位、またはアプリ全体でSSRを無効化できます**（Selective SSR）。

- ルートごとに`ssr: false`を指定すると、そのルートは`loader`/`beforeLoad`がサーバー側で実行されなくなり、コンポーネントのサーバーレンダリングも行われなくなります。実質的にCSRと同じ挙動になります
- `createStart`の`defaultSsr: false`を使えば、アプリ全体のデフォルトをCSR寄りに倒すこともできます

ただし、Selective SSRはあくまで「サーバーでレンダリングしなくなる」だけで、**初回リクエストを捌くサーバー自体は依然として必要**です。サーバーごと不要にしたい場合は、これとは別の**SPAモード**を使います。

```ts
// vite.config.ts
tanstackStart({
  spa: {
    enabled: true,
  },
}),
```

SPAモードを有効にすると、ビルド時に追加のプリレンダリングが走り、静的な「シェル」HTML（`_shell.html`）があらかじめ生成されます。このシェルの中身はルートのコンテンツではなくローディング表示（pending fallback）なので、分類としてはSSGというより「CSR＋事前生成した外枠」です。コンテンツ入りのHTMLを事前生成したい場合は、別途prerender機能によるページ単位のSSGも可能です。

結果として、TanStack StartでもSPAモードを使えば、**デプロイ先を静的ファイルを配信できるCDNだけで完結させる**構成にできます。「TanStack Start＝常駐サーバーが必須」というのは思い込みで、実際には「デフォルトはSSR、必要なければCSR/SSG寄りに倒せる」というのが正確な理解でした。

ただし1点注意が必要です。SPAモードにしても、Server FunctionsやServer Routesといったサーバー機能自体は「使おうと思えば使える」状態のままです。それらを実際に呼び出す設計にすると、結局そのエンドポイントを処理するサーバーが必要になります。本当にゼロサーバー構成にしたいなら、SPAモードにするだけでなく、そもそもこれらのサーバー機能を使わない設計にする、という意識が必要です。

## 7. 比較表：TanStack Router vs TanStack Start

ここまでの整理をまとめると、こうなります。

| 項目 | TanStack Router単体 | TanStack Start |
| --- | --- | --- |
| デフォルトのレンダリング戦略 | CSR | SSR（ルート/アプリ単位でCSR・SSG寄りに変更可） |
| 実行時の常駐サーバー | 不要 | デフォルトは必要（SPAモードなら不要にできる） |
| デプロイ先 | 静的ホスティング/CDNのみ | Node.js等のサーバーランタイム（SPAモード時はCDNのみでも可） |
| `loader`の実行場所 | ブラウザのみ | サーバー・ブラウザ両方（SSR時） |
| Server Functions / Server Routes | なし | あり |
| 型安全なルーティング | あり | あり（Routerの機能をそのまま継承） |
| 向いている用途 | 常駐サーバーを持ちたくない構成（社内ツール、SEO不要な認証付き管理画面、静的配信で完結させたいアプリなど） | SEOが必要な公開サービスや、フルスタックで一体的に作りたいプロダクト |

こうして並べると、**TanStack StartはTanStack Routerの上位互換というより、「サーバー機能が必要になったときの拡張先」**という位置付けの方が正確だと感じます。ルーティングまわりの書き味はほぼ共通なので、「最初はTanStack Routerで作り、あとからサーバー機能が必要になったらStartに寄せる」という移行もしやすそうです。

## まとめ

最初に感じていた「SSR・CSR・SSG・SPAがごちゃごちゃ」という混乱は、**「アプリケーション構造（SPA/MPA）」と「レンダリング戦略（CSR/SSR/SSG）」という別々の軸を一緒くたに考えていた**ことが原因でした。この2軸を分けて整理すると、それぞれの技術がどこに位置するかがはっきりします。

- **TanStack Router単体**：常にCSR（かつSPA）。ビルド後は静的ファイルのみで、常駐サーバー不要
- **TanStack Start**：デフォルトはSSRだが、`ssr: false`/SPAモードによってCSR・SSG寄りの構成にも倒せる、柔軟なフルスタックフレームワーク

つまり「TanStack RouterかTanStack Startか」は「CSRかSSRか」という二択そのものではなく、**「サーバー機能（Server Functions・API Routes・SSR）が必要かどうか」で選ぶもの**というのが、自分の中での結論です。SSRが持つメリット（SEO、初期表示の体感速度など）が本当に必要な要件なのかを見極めることが、結局一番大事な判断軸になりそうです。
