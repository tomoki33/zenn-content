## はじめに

最近、業務の中でセキュリティの話題を目にする機会が増えました。サプライチェーン攻撃のニュースも多く、ふと「普段何気なく打っている `npm install` が、実際に何をしているのか説明できない」と気づきました。

そこで、公式ドキュメントを読み、実際に動かして整理しました。この記事では次の3つを扱います。

- `npm install` で何が起きているのか
- どこにリスクがあるのか
- どう防ぐのか

:::message
攻撃手法の解説ではなく、自分の環境を守るために仕組みを理解することが目的です。検証は使い捨てのコンテナの中で行い、スクリプトの検証には無害なダミーだけを使いました。
:::

## 1. npm installで何が起きているのか

`npm install` は、次の流れで進みます。

| ステップ | 起きること | 関わるコード |
|---|---|---|
| ① 読み込み | `package.json` を読む | 自分のコード |
| ② 依存の解決 | 必要な依存のツリーを組み立てる | 自分が選んでいない依存も含む |
| ③ ダウンロード | レジストリから取得して `node_modules` に展開する | 他人のコード |
| ④ スクリプト実行 | 各パッケージの `preinstall` / `install` / `postinstall` を実行する | パッケージの作者が書いたコマンド |
| ⑤ 完了後 | アプリから `import` したり、`npm run dev` で動かしたりする | 他人のコード |

押さえておきたいのは、次の点です。

**② 自分が選んでいない依存も入る。** たとえば `is-odd` を1つ入れるだけで、その依存の `is-number` も入ります。見えていない依存にもスクリプトがあれば、④で実行され得ます。

**④ 作者が書いたコマンドが、確認なしに自動で実行される。** 依存パッケージでは、`preinstall` → `install` → `postinstall` の順に実行されます。

**補足：lockfile に記録が残る。** `package-lock.json` には、各パッケージの取得元（`resolved`）とハッシュ（`integrity`）が記録されます。スクリプトを持つパッケージには `hasInstallScript` という印が付くので、どの依存が④で動き得るかは、lockfile から分かります。

## 2. どこにリスクがあるのか

上のステップごとに、考えられるリスクを整理します。

| ステップ | 考えられるリスク |
|---|---|
| ② 依存の解決 | 名前を似せた偽のパッケージを入れてしまう。見えていない依存のどこかが乗っ取られている |
| ③ ダウンロード | 正規のパッケージの更新に、悪意あるコードが混入する（メンテナのアカウント乗っ取りなど） |
| ④ スクリプト実行 | 自分と同じ権限で、確認なしにコマンドが実行される。ホーム配下の認証情報などが読まれ得る |
| ⑤ 完了後 | `import` や `npm run dev` の時点で、悪意あるコードが動く |

実例として、2025年9月に確認された「Shai-Hulud」があります（GitHub の公式ブログ「[Our plan for a more secure npm supply chain](https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/)」）。人気パッケージのメンテナのアカウントが侵害され、悪意ある `postinstall` を仕込んだバージョンが公開されました。そのバージョンを `npm install` した環境では、スクリプトが自動で実行され、npm トークンを含む複数の種類の秘密情報が狙われました。GitHub は500以上の侵害パッケージを削除しています。③から④へとつながった例です。

影響が大きいのは④です。インストールした瞬間に、確認なしで、自分と同じ権限で動くためです。一方で、④を止めても⑤は防げません。インストール時に何もしなくても、あとで `import` や実行された時点で動けるからです。

## 3. 実際に確認する

2章で書いた「スクリプトが確認なしに動き、手元の情報が見える」が実際に起きるのか、使い捨てのコンテナで確かめました。本物の悪意あるコードの代わりに、偽の認証情報（中身は `DUMMY`）だけを置き、`~/.ssh` などが存在するかを表示するだけの無害なダミーを使っています。ファイルの中身の読み取りも、外部通信もしません。

```js
// ダミーの postinstall（抜粋）。存在確認だけで、中身は読まない
console.log('exists?', fs.existsSync(path.join(home, '.ssh')));
```

npm 11.21.2 でそのまま `npm install` すると、スクリプトが実行され、`~/.ssh` などの存在と、`TOKEN` を含む環境変数名が見えました。`--ignore-scripts` を付けると、実行されませんでした。npm 12.2.2 では、何も付けなくてもブロックされました。

:::message
スクリプト実行の検証は、npm 11.21.2 と 12.2.2、ローカルの tarball（`file:` 依存）で行いました。実際のレジストリ経由でのスクリプト実行は未検証です。
:::

## 4. どう防ぐのか

リスクのステップごとに、対策を対応させます。

| ステップ | 対策 |
|---|---|
| ② ③ | 公開直後のバージョンを避ける（`min-release-age`）。lockfile で固定する（`npm ci`）。新しく増えた依存を確認する |
| ④ | 依存のスクリプトを許可制にする（npm 12 のデフォルト、`--ignore-scripts`） |
| ⑤ | 信頼できないコードは隔離して実行する。認証情報を平文で置かない |

### ④ スクリプトの許可制

npm 12.0.0（2026-07-08）の changelog に、次の変更が記載されています。

> Dependency lifecycle scripts are now blocked by default unless allowed by the root package's `allowScripts` policy.

つまり、依存のスクリプトは、許可したものだけが実行されます。pnpm は v10 で、先に同じ方針になっています。

npm 12 より前では、デフォルトでは止まりません。npm 11.21.2 は警告を出すだけで実行し、npm 10.8.2 には許可制のコマンド自体がありません。その場合は `--ignore-scripts` が基本になります。また、npm 12 の対応 Node は `^22.22.2 || ^24.15.0 || >=26.0.0` で、Node 20 は対応外です。バージョンは `npm -v` で分かります。

npm 12 でブロックされたパッケージがあっても、インストール自体は成功し、警告が出ます。必要なものがあれば、次の流れで許可します。

1. `npm install-scripts ls` で、未承認のスクリプトを一覧する
2. 内容を確認し、信頼できるものだけを `npm install-scripts approve <pkg>` で承認する
3. `npm rebuild` で、承認したスクリプトを実行する

承認した内容は `package.json` の `allowScripts` に記録されるので、コードレビューの対象にできます。許可しなかったパッケージは、そのスクリプトが走らないだけです。ネイティブのビルドなどにスクリプトが必須のライブラリは、許可しないと動かない可能性があります。

なお、ブロックの対象は依存のスクリプトです。自分のプロジェクト（root）のスクリプトは、npm 12 でも実行されました。他人のリポジトリを `git clone` して `npm install` した場合、そのリポジトリ自身のスクリプトは走ります。

### ② ③ 公開直後を避ける

`min-release-age` に日数を指定すると、公開からその日数以上たったバージョンだけが対象になります。公開直後のバージョンは、悪意の有無が広く検証される前の段階にあたるため、一定の日数を待ってから入れるようにします。`.npmrc` に書くと、コマンドごとに指定しなくても効きます（npm 11.21.2 で確認）。

```
# .npmrc
min-release-age=3
```

注意点が2つあります。古い npm（10.8.2 で確認）では、エラーも警告もなく無視されます。また、lockfile に記録済みのバージョンには効きません。セキュリティ修正をすぐ取り込みたいときは、`min-release-age-exclude` で除外できます。

### 普段やる3つ

項目が多いと続かないため、優先度の高いものを3つに絞ります。

1. **依存のスクリプトを許可制にする。** npm 12 ならデフォルトで有効。それ以前の npm や他人のリポジトリでは `--ignore-scripts` を使う
2. **公開直後のバージョンを避ける。** `min-release-age` を使う
3. **認証情報を平文で置かない。** `.env` や `~/.npmrc` に長期のトークンを書いたままにせず、短命・最小権限のものを使う。実行された時点で読まれ得るため、読まれても被害が小さい状態にしておく

会社のPCでは、これに加えて、社内ルールと許可されたツールの範囲を確認します。怪しいと思ったときは、自分で調べ続けず、セキュリティ担当へ報告します。

### 怪しいものを入れてしまったとき

1. 会社のPCなら、まずセキュリティ担当へ報告する（以降の手順は、会社の指示が優先）
2. ネットワークから切り離す（または作業を止める）
3. そのPCに置いてあった認証情報を、別の端末から失効・再発行する（GitHub、npm、クラウド、社内システムなど）

削除より先に、認証情報を無効にします。読まれた後では、ファイルを消しても意味がないためです。そのPCでの作業再開は、調査が済んでから判断します。

## まとめ

- `npm install` は、依存の解決、ダウンロード、スクリプト実行の順に進み、**他人が書いたコマンドが、自分の権限で自動実行され得る**
- リスクは、偽のパッケージ、更新への混入、スクリプトの自動実行、実行時のコード、とステップごとに分かれる
- npm 12 では④の自動実行がデフォルトで止まる。ただし、それ以前の npm、自分のプロジェクトのスクリプト、実行時のコードは対象外
- 普段は「スクリプトを許可制にする」「公開直後を避ける」「認証情報を平文で置かない」を意識する

ほかのパッケージマネージャも、インストール時にコードが走り得る構造は似ています。今回確認したのは npm だけです。
