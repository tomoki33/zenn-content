普段は Web エンジニアをしています。今回、初めてiPhoneアプリ（Expo）を作って、App Store の審査に出すところまで行きました。

やってみて感じたのは、コードを書くより、出すまでのほうが大変だったということです。実際に感じた順に、違いを書きます。


## バックエンドは Web とほぼ同じだった

ネイティブアプリは、サーバー側にも特別な仕組みが必要なのかと思っていましたが、そんなことはありませんでした。サーバー側は、Web と同じものがそのまま使えました。

画面側も、React Native のおかげで、ほぼ Web と同じ感覚で作れました。書き方は React で、違うのはスタイルくらいです（CSS ではなく、JS のオブジェクトでの記載でした）。

違いが出るのは、カメラやヘルスケア、Apple ログインのような、端末の機能とつなぐ部分でした。ここは本来、iOS なら Swift、Android なら Kotlin といった専用の言語が必要な領域です。ただ、それらで作られたライブラリが npm に公開されていて、`npm install` で入れて JS から呼べるようになっていました。実際、今回は Swift を書く場面はほとんどなく、端末の機能も、ほぼ npm のライブラリで済んだためここは実際にやってみて気づいた意外な点でした。



## 諸々ツールの登録がいり、お金もかかる

まず、Apple Developer Program への登録が必要です（年額 99 ドル）。これがないと、実機に入れるための証明書も作れず、App Store にも出せません。ビルドに使った Expo の EAS は、無料枠でも動かせます。

もう一つ、Web の感覚とズレたのが環境変数です。開発中は `.env.local` に Supabase の URL を書いて動いていましたが、あれは開発サーバーが手元のファイルを読んでいただけです。本番ビルドは EAS のクラウドで作られるので、`.env.local` は送られません。`eas env:create` で本番用に登録しないと、ログインもバックアップも動かないアプリができあがります。

## 公開前に触ってもらうのが、Web より面倒

Web ならデプロイすればすぐ友人に見てもらえます。ネイティブはちょっと違いました。

公開前に実機で配る方法として、Apple のTestFlightがあります。ベータ版の配信用の仕組みで、招待リンクを送ると、相手は先に TestFlight のアプリを入れて、その中から自分のアプリを入れることになります。友人にすぐ触っても炊いたかったもののアプリを2つ入れてもらう手間が発生してしまうことに戸惑いを覚えました。。

友人には、App Store から普通のアプリとして入れてもらいたかったので、友人への配布は 今回はTestFlight を使わず、公開審査にそのまま進むことにしました。

ただ、自分の動作確認には TestFlight を使いました。WebでいうDev環境確認みたいに捉えていて、ここで開発サーバでは見えないいくつかのバグも見つかりました。

## 審査に必要な準備が思ったより多い

提出する前に用意するものが結構あります。

- 画面サイズごとのスクリーンショット（6.9 インチ、6.5 インチ）
- プライバシーポリシーと利用規約を載せた、公開URLのページ（LP も作りました）
- アプリがどんなデータを集めるかの申告（栄養成分表示のようなもの）
- 年齢制限の質問への回答
- 審査員向けのメモ
- アカウントを作れるアプリは、アカウント削除の機能

それぞれに Apple の規約があって、読みながら揃えるのが大変でした。
AI使えば用意比較的早くできるものの、何を出すのか中身は確認支度その確認が意外と大変でした。（初めてで何が作られてるのかもよく分からず。。）

## アプリ名は重複して公開ができない

最初は「PLATE」という名前で登録しようとしました。
App Store Connect でアプリを作る段階で、「入力したアプリの名前はすでに使用されています」と出ました。

IOSアプリでは名前が重複するアプリは同じ名前で公開できないようです。公開前に名前を変更する必要が生じてしまいました
幸い今回はサブタイトルつけることで大きな手戻りは回避できましたが、知らずにこの名前ベースでデザインとかも考えていたので事前に知らなかったことで大分手戻りになるところでした。

用意していた名前が取れるかは、早めに確かめておくべきでした。

## 審査に出しても、一発では通らない

提出して終わりではありませんでした。
待っていたら、Guideline 2.1「Information Needed」という返信がAPPLEから届きました。

審査が落ちたわけではなく、審査の実績が少ない新規アカウントに対する追加の質問でした。
求められたのは次の6つです。

1. 実機で撮った画面録画（起動から、ログイン、アカウント削除まで）
2. アプリの目的と対象
3. 主な機能の使い方
4. 使っている外部サービスの一覧
5. 地域による違い
6. 規制のある分野かどうか

大分厳しいなというのが率直に感じたことです。
Webはその点公開に際しこういった制約等がなかったので大分楽なんだなと感じました。
初めてなのもあり各種整理・理解するのにかなり戸惑いました。

## CICD的なのがない

Web なら、直したらCICD等使用でデプロイ可能です。
ネイティブだと、普通は修正のたびに審査に出すことになります。

ただ、ネイティブアプリでも、JS だけの修正なら審査なしで配れる仕組み（EAS Update）がありました。これは Web のデプロイに近い感覚でした。

2回目以降のデプロイ時の審査をスキップする設定（`expo-updates`）があるらしくこちらは意図的に設定しないといけないものでした。
事前に入れておくことを知らずだったのでここはAIに指摘され導入できました。

個人開発レベルでもWebのように気軽にデプロイとはいかなそうなのでそこはちゃんと整理しながら今後のアップデートもする必要性を感じました。

## おわりに

Webの感覚で初めてネイティブアプリに取り組みましたが、大きな違いがあったのは意外にもコーディングのところではなく、審査等公開前の手続き的なところでした。
AIもある、かつWebと大分近い感覚で開発自体はできるためWebエンジニアにも大分手の届きやすいものだなと感じました。
