## はじめに

個人開発、モチベーションがうまく保てず何度も中途半端頓挫してきました。

アイデア自体は思いつく。作り始めもする。AIで開発できるとはいえ、インフラの設計や技術選定、リファクタリング、アイディアが壮大すぎて収拾つかなくなる等に時間を溶かしているうちに熱量が切れて止まる——というパターンを何度も繰り返してきました。

今回、ある小さなアイデアを「今日中に動くものにする」ことを目標に据えて実際に作り切り、複数知人に使ってもらうところまで持っていけました。この記事では、そのアイデアの中身（そっちは別記事で書く予定です）ではなく、**なぜ今回は頓挫せずに動くところまで行けたのか**を、技術選定の話を軸に整理しておこうと思います。

結論から言うと、Next.js + Supabase + Vercelという組み合わせが「作り切る」ことに驚くほど貢献してくれた、というのがこの記事の主張です。

## とりあえず動くもの→使ってもらう→フィードバック

個人開発を頓挫させてきた自分の過去を振り返ると、共通していたのは「誰にも使われていない状態のまま、機能や設計を磨き続けてしまう」ことでした。使う人の反応がないまま作り続けると、何を優先すべきかの判断基準がなくなり、結果として完成度に対する自分の中の基準だけが際限なく上がっていって、いつまでも「使える状態」に到達しない。

今回はその反省から、**「とりあえず動くものを作る → 実際に誰かに使ってもらう → フィードバックをもらって次を決める」というサイクルを、可能な限り早く一周させる**ことを最優先にしました。実際、最初のバージョンはかなり最小限の機能だけで知人に使い始めてもらい、そこから先の機能追加は一旦止めて、実際の利用の中でのフィードバックを待つという判断をしています。機能を足せば足すほど「良いもの」に近づく気がしてしまいますが、使われていない機能はいくら足しても価値を生みません。


## なぜこの組み合わせが良かったか

Next.js、Supabase、Vercel、それぞれ単体の技術解説記事は世の中に山ほどあります。ここで書きたいのは個々の機能紹介ではなく、**この3つを組み合わせたときに何が起きるか**という話です。

一言でまとめると、この3つに共通しているのは「インフラに関する意思決定を、可能な限り自分の手から奪ってくれる」という性質です。個人開発でボトルネックになるのは大体の場合、実装力ではなく意思決定の数そのものなので、これが効きます。

### Next.js（Server Actions）: 「API設計」という意思決定が消える

普通、フロントエンドとバックエンドが分かれている構成だと、「どんなエンドポイントを切るか」「レスポンスの形式をどう設計するか」「フロントとどう契約するか」といった設計判断が必要になります。小さいアプリであってもこの設計自体には地味に時間がかかりますし、後から仕様が変わるたびに両側を直す必要も出てきます。

Server Actionsを使うと、フォームの送信がそのままサーバー側の関数呼び出しになります。つまり「API層」という概念自体がほぼ消えます。作ったのは実質、DBを読み書きする関数と、それを呼ぶフォームだけ。設計すべきものが減ると、そのぶん「何を作るか」そのものに頭を使えます。

### Supabase: 「DB選定・構築・認証」という意思決定が消える、かつ使い捨てにならない

DBをどこに立てるか、マイグレーションはどう管理するか、接続認証はどう組むか——これも個人開発が止まりがちなポイントです。Supabaseはここを「プロジェクトを作る」の数クリックで済ませてくれます。

ここで個人的に重要だと思っているのは、Supabaseの中身が素のPostgreSQLだという点です。つまり「とりあえず作った検証用のもの」が、そのまま「本番でも通用するもの」になります。早く作れることと、後で作り直しが必要になることは本来トレードオフになりがちですが、Supabaseはその両方を同時に満たしてくれる。個人開発では「検証用に雑に作ったものを結局本番用に作り直す」タイミングで力尽きることが多いので、これは地味に効いています。

https://supabase.com/

### Vercel: 「デプロイ・運用」という意思決定が消える

サーバーの面倒を見る、証明書を更新する、CIを組む——こういった運用作業は、個人開発の熱量を確実に削ってくれます。Vercelは`git push`が本番反映になり、cronジョブも設定ファイルに書くだけで済みます。運用等を必要以上に考える手間を削減できたのは大きかったです。

https://vercel.com/

### 共通点：意思決定の総量を減らすことが、サイクルの速さに直結する

この3つに共通しているのは、繰り返しになりますが「インフラ判断を極小化して、プロダクトそのものの判断にリソースを全部使えるようにする」という点です。

これが、冒頭で書いた「とりあえず動くもの→使ってもらう→フィードバック」のサイクルと直結します。インフラの意思決定に使う時間が減れば減るほど、最初の「動くもの」にたどり着くまでの時間が短くなり、結果としてフィードバックをもらえるタイミングも早くなる。技術選定そのものが、思想を実現するための手段になっている、という感覚が今回強くありました。

## この構成が向かない場面

正直に弱点も書いておきます。

- **RLSを設定していない前提の設計**（サーバー側のservice role key経由でしかDBにアクセスしない構成）は、今回のような「サーバー専用アプリ」だからこそ成立するもので、複数テナントが同一DBに直接アクセスするようなSaaS的な構成にそのまま持っていくには追加の設計が必要になります
- Server Actionsに寄せた設計は、Next.jsという枠組みへの依存を強めます。将来的に別のフロントエンドを足したり、モバイルアプリからも叩きたい、となったときには素直なREST/GraphQL APIを別途切り出す必要が出てきます

つまりこの構成は「最初の一歩を最速で踏み出すため」の構成であって、あらゆる規模・要件に対して万能というわけではありません。ただ、個人開発の多くは「最初の一歩を踏み出せずに終わる」のが個人として問題だったので、そこに対する処方箋としては今のところかなり効いていると感じています。

## まとめ

今回、思いついたアイデアを実際に動くところまで作り切り、知人に使ってもらい始めることができました。今は機能を追加するのではなく、実際の利用から出てくるフィードバックをもとに改善している段階です。

「とりあえず動くものを作って、誰かに使ってもらう」を早く一周させたい人には、かなりおすすめできる構成です。
